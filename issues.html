In the main loop (original/OPIL-source.bas:471-492) the three scene tests are sequential IFs, not an ELSE chain. The cutscene block sets sc to 1 or 2, and the very next IF retests sc in the same pass, so one iteration can play cutscene then dialogue then object. INC c therefore counts loop iterations, not scenes.

CORRECTED 2026-09-08. This issue previously claimed the effect was that 'IF c=10 THEN GOTO intro' restarts the intro much sooner than ten scenes. That is backwards. Every iteration plays at least one scene and often two or three, so ten iterations deliver at least ten scenes and the intro comes back LATER than a scene count of ten, not sooner. The real symptom is variance rather than brevity: how much story plays before the restart differs run to run.

Scenes per iteration, by the sc value on entry. Entering at sc=0: cutscene runs, then sc=RND(2)+1 is 1 or 2, so a second scene always follows; if that second scene is the dialogue branch its own re-roll lands on 2 one time in five, adding an object. So 2 scenes, or 3 about one time in ten. Entering at sc=1: dialogue, plus an object one time in five, so 1 or 2. Entering at sc=2: object alone, 1. Hard bounds on a full cycle are therefore 10 scenes at minimum and 30 at the unreachable maximum, with real runs somewhere in between (not simulated, so no average is claimed here).

Evidence that the fall-through is deliberate: both chained re-rolls carry steering comments, 'REM pref cut' on the dialogue branch and 'REM pref dialog' on the object branch, so the author was choosing what tends to follow what. Against that, sc is never reset at intro (the 'sc=0 debug line at :445 is commented out), so a restart resumes from whatever scene type was pending.

Still open as a question. The counter behaviour follows from a structure that looks intentional, so confirm the author's intent before changing anything.

objectcontentdeferredOPIL-source.bas · created 2026-08-05 · updated 2026-08-07

WONTFIX - not waste, headroom. The maintainer's call on 2026-09-08: OPEN PILANTRA is a BASIC framework as much as a demo, and the author may well add to the portraits later. 176 is a clean 16x11 grid; trimming it to fit today's draw loop would optimise against the author's intent for a saving nothing currently needs.

What the survey established, so it need not be redone. The ten portraits at original/OPIL-source.bas:42-265 are each DIM name(176) AS BYTE. The draw loop at :672-682 runs x 0..14 and y 0..9 indexing name(x+y*16), so the highest index read is 14+9*16=158. Two distinct kinds of slack follow. Trailing: indices 159 up, the spare 11th row, which is the only part a lower DIM would reclaim and the source of the 18-byte figure (17 if ugBASIC allocates 0..175 rather than 0..176; never confirmed which). Interior: index 15 of every row, 10 bytes, unreachable because the stride is 16 but the loop stops at 14. Reclaiming the interior would mean re-striding to 15 and changing tools/art.py and both draw subroutines. Neither drawchrl nor drawchrr (:847-862) would need touching for a trailing trim alone.

If a memory ceiling is ever hit, the spare row and column are the first place to look, and the numbers above are the budget.

WONTFIX - not needed. tools/screenpeek.py has been removed rather than left in tools/ as a half-working script beside working ones.

What the attempt established, so it need not be re-derived:
- XRoar's GDB stub listens on 127.0.0.1:65520 with -gdb, and the packet 'm0400,200' returns the 512-byte 32x16 text screen.
- Decoding: bit 7 clear is a character cell whose low 6 bits are the character ($00-$1F is '@A-Z[\]^_', $20-$3F is ' !"#...?'); bit 7 set is an SG4 graphics cell.
- ATTACHING HALTS THE CPU. A one-shot read of an already-running program works and was proven (it decoded both the boot screen and a mid-scene graphics screen). Sampling repeatedly needs a continue/interrupt cycle that was never got right - a plain 'c' followed by 0x03 drops the connection.
- The stub serves one client at a time; opening a fresh connection per sample wedges it.
- MCP screen capture failed for window AND full-display capture, which points at macOS Screen Recording permission rather than anything in this repository.

CORRECTED 2026-09-08 by the issue 7 capture work. The conclusion above that MCP capture failure 'points at macOS Screen Recording permission' is WRONG. Screen Recording is granted, and scripted capture of the emulator window works today with a one-line shell command:

screencapture -x -o -l <window_id> out.png

The MCP server is what is broken: it enumerates windows and displays correctly but times out on every pixel capture, reporting itself that the permission preflight passed and the stall is inside ScreenCaptureKit.

This does not revive the GDB-stub approach, which remains a dead end for the reasons above, and it does not give a script the decoded TEXT of the screen, which is what this issue originally wanted. It does mean scripted visual verification is possible, so the premise that screen checks always need the maintainer is no longer true. Left as wontfix rather than reopened: the pixel route belongs to whoever needs it next, and CONTRIBUTING.md still states the old premise and should be revisited.
